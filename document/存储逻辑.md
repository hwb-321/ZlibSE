# 存储逻辑

## 说明

本文档描述的是后续对象存储方案下，推荐采用的精简存储流程。

设计目标：
- 适合作为求职简历项目 demo
- 后端不承担大文件中转流量
- 前端通过预签名 URL 直传、直下对象存储
- 文件信息与书籍业务信息拆开
- `books -> stored_files` 保持单向关系

## 推荐接口

推荐使用 3 个接口：
- `POST /api/files/upload-url`
- `POST /api/files/upload-complete`
- `GET /api/files/{file_id}/download-url`

说明：
- 路由使用 `files`，不直接暴露 `cos`
- `cos` 只是底层实现，不应直接作为业务接口命名

## 接口职责

### 1. `POST /api/files/upload-url`

职责：
- 校验用户登录态
- 校验文件类型、大小、用途
- 由后端生成对象 key
- 由后端签发预签名上传 URL

推荐请求字段：
- `filename`
- `contentType`
- `size`
- `kind`

推荐返回字段：
- `objectKey`
- `uploadUrl`
- `expiresIn`

说明：
- `kind` 推荐取值为 `book` 或 `cover`
- 前端不应直接决定完整对象路径
- 对象 key 必须由后端生成

### 2. `POST /api/files/upload-complete`

职责：
- 前端上传成功后通知后端
- 后端校验对象是否存在
- 后端写入 `stored_files`
- 返回 `file_id`

推荐请求字段：
- `objectKey`
- `etag`
- `size`
- `contentType`
- `kind`

推荐返回字段：
- `fileId`

说明：
- 该接口只负责写文件记录
- 不直接写书籍业务信息

### 3. `GET /api/files/{file_id}/download-url`

职责：
- 校验用户是否有下载权限
- 根据 `file_id` 查询文件记录
- 签发预签名下载 URL

推荐返回字段：
- `downloadUrl`
- `expiresIn`
- `filename`

## 上传顺序

推荐上传流程：

1. 前端选择文件
2. 前端请求 `POST /api/files/upload-url`
3. 后端根据 `kind` 生成 `bucket` 和 `object_key`
4. 后端返回预签名上传 URL
5. 前端直接上传到对象存储
6. 前端请求 `POST /api/files/upload-complete`
7. 后端写入 `stored_files`
8. 后端返回 `file_id`
9. 前端将 `file_id` 再提交给书籍创建或编辑接口

## 下载顺序

推荐下载流程：

1. 前端请求 `GET /api/files/{file_id}/download-url`
2. 后端根据 `file_id` 查询文件记录
3. 后端签发下载 URL
4. 前端使用该 URL 发起下载

## 数据库存储方式

推荐数据库结构：
- `books` 保存书籍业务信息
- `stored_files` 保存对象存储定位信息

关键关系：
- `books.book_file_id -> stored_files.id`
- `books.cover_file_id -> stored_files.id`

说明：
- 这是单向关系
- `books` 引用文件
- `stored_files` 不反向记录自己属于哪本书

## 存储桶设计

推荐先采用“单桶 + key 前缀分类”的方案。

推荐方式：
- 正文文件：`books/{yyyy}/{mm}/{uuid}.{ext}`
- 封面文件：`covers/{yyyy}/{mm}/{uuid}.{ext}`

说明：
- 配置简单
- 结构清晰
- 很适合 demo 项目

数据库中建议保留这些存储定位字段：
- `bucket`
- `region`
- `object_key`

## stored_files 精简字段建议

`stored_files` 建议保留以下字段：
- `id`
- `bucket`
- `region`
- `object_key`
- `original_filename`
- `content_type`
- `size`
- `etag`
- `kind`

说明：
- 这是面向 demo 的最小可用设计
- 不额外保留 `status`、`uploaded_by`、`created_at`、`updated_at`

## 实施顺序

### 第一步：新增 `stored_files` 表

目标：
- 先完成数据库结构拆分

要做的事：
- 新增 `stored_files` 模型
- `books` 增加 `book_file_id` 和 `cover_file_id`

### 第二步：封装存储层

目标：
- 不让路由直接操作对象存储 SDK

要做的事：
- 新增统一存储服务
- 提供生成上传 URL、下载 URL、检查对象是否存在的方法

### 第三步：实现上传接口

目标：
- 落地 `upload-url` 和 `upload-complete`

要做的事：
- 先实现文件上传闭环
- 先让文件记录能独立工作

### 第四步：改造书籍创建与编辑流程

目标：
- 书籍接口改为接收 `book_file_id` 和 `cover_file_id`

要做的事：
- 前端先上传文件
- 再提交书籍业务数据

### 第五步：实现下载接口

目标：
- 落地 `GET /api/files/{file_id}/download-url`

要做的事：
- 按 `file_id` 生成下载链接
- 前端改为通过文件 ID 获取下载 URL

## 总结

推荐采用的精简方案是：
- 前端直传对象存储
- 后端负责签名和元数据落库
- `stored_files` 保存文件定位信息
- `books` 只保存业务字段，并通过 `book_file_id`、`cover_file_id` 单向引用文件
