# 后端接口说明

## 说明

本文档按当前项目源码整理，重点说明每个接口的：

- 方法
- URL
- 会做什么
- 主要逻辑
- 是否访问数据库
- 是否访问一级缓存 / Redis

说明约定：

- 一级缓存：指进程内 `TTLCache`，实现位置是 `fastapi_app/services/local_cache_service.py`
- Redis：包括 Redis KV 缓存、Redis 锁、`user:{id}:auth_token_version`、`user:{id}:profile`、`user:{id}:favorite_version`、`user:{id}:favorite_ids`、`books:cache_version`、`book:{id}:detail_cache_version`、未绑定封面文件数量控制用的 Redis Set
- 布隆过滤器：是进程内内存结构，不属于一级缓存，也不属于 Redis
- “访问数据库”按接口实际代码路径判断；如果缓存命中时不查库，会明确写出来
- 需要登录的接口统一会先走 JWT 鉴权；JWT 中写入的是 `auth_version`；默认鉴权依赖会先读 Redis `user:{id}:auth_token_version`；只有当 Redis 中存在该值且与 token 内 `auth_version` 一致时，才会继续优先读一级缓存中的 `user:{id}:profile`，一级缓存未命中后再读 Redis `user:{id}:profile`；如果 Redis 中没有该认证版本，或用户基础信息缓存仍未命中，就会直接查 `users` 表，并回写 Redis 与一级缓存

当前 `config.yaml` 默认配置表现：

- `security.captcha_enabled = false`
- `redis.enabled = true`
- `local_cache.enabled = true`
- `async_parse.enabled = true`
- `async_parse.mode = on`
- `benchmark.mock_upload_enabled = false`
- `redis.bloom_trusted_ttl_seconds = 10`

缓存开关组合约定：

- `redis.enabled = true` 且 `local_cache.enabled = true`：一级缓存 + Redis + 数据库
- `redis.enabled = true` 且 `local_cache.enabled = false`：Redis + 数据库
- `redis.enabled = false`：只有数据库；此时本地一级缓存也不会单独启用

当前仓库已经只保留新实现：

- 不再支持旧的本地文件兼容路径
- 不再支持旧的 `upload_tasks` 方案
- `async_parse.mode` 只保留 `off / on`

当 `benchmark.mock_upload_enabled = true` 时：

- 文件上传走 `server-mock`
- 跳过真实上传
- 跳过真实解析和消息队列投递
- `complete` 会直接写入默认 `file_parse_results`
- `download` 统一指向配置里的固定 mock 对象

## 书籍接口

当前代码只支持创建、查询、删除书籍，不支持直接修改书籍信息。

当前返回结构约定：

- `/api/books`、`/api/users/me/favorites`、`/api/users/me/uploads` 只返回书籍简要信息：`id / title / author / language / file_type / file_size / cover_image_path`
- `/api/books/{book_id}` 返回完整详情；在简要信息基础上额外包含 `isbn / category / year / book_file_id / cover_file_id / file_path`
- `file_path` 和 `cover_image_path` 都指向 `/api/files/{file_id}/download`；后端只返回对象访问地址，不再直接代理文件内容

| 方法 | URL | 会做什么 | 主要逻辑 | 是否访问数据库 | 是否访问一级缓存 / Redis |
|---|---|---|---|---|---|
| POST | `/api/books` | 用已上传并解析完成的正文文件创建书籍 | 鉴权；校验 `storedFileId` 对应文件存在、属于当前用户、`kind=book`、`bind_status=unbound`、`parse_status=done`；如果传了 `coverFileId`，也会校验封面文件归属与类型；创建 `books` 记录；创建 `uploaded_books` 记录；正文和封面文件 `ref_count + 1`，并标记为 `bound`；手动封面被采用时会从 Redis 未绑定封面集合里移除；提交后递增 Redis `books:cache_version`；同时把书 id 加入进程内布隆过滤器 | 是，查询 `stored_files`，写入 `books`、`uploaded_books`，更新 `stored_files` | 不访问一级缓存；会递增 Redis 全局书籍集合版本；会删除 Redis/一级缓存中的文件元数据缓存；会改 Redis 未绑定封面集合；会使用进程内布隆过滤器 |
| GET | `/api/books/count` | 获取书籍总数 | 先按 Redis `books:cache_version` 构造缓存 key；优先读一级缓存，一级缓存未命中再读 Redis；两层都未命中时统计 `books` 表数量，并同时回填 Redis 与一级缓存；新建书籍和删除书籍时会通过递增 `books:cache_version` 让旧计数缓存自然失效 | 是，缓存未命中时查询 `books` | 会读写一级缓存；会读写 Redis |
| GET | `/api/books` | 获取书籍分页列表 | 优先支持游标分页：读取 `lastId / pageSize`，用 `WHERE id < lastId ORDER BY id DESC LIMIT pageSize` 查询；为了兼容旧调用，未传 `lastId` 时仍支持 `page / pageSize` 并回退到 `OFFSET + LIMIT`；`pageSize` 超过配置上限会直接报错；缓存 key 会携带 Redis `books:cache_version`，游标分页与页码分页分别命中各自缓存；优先读一级缓存，一级缓存未命中再读 Redis；两层都未命中时再查 `books` 表并同时回填 Redis 与一级缓存 | 是，缓存未命中时查询 `books` | 会读写一级缓存；会读写 Redis |
| GET | `/api/books/{book_id}` | 获取书籍详情 | 先看进程内布隆过滤器当前是否仍处于“可信窗口”；如果仍在 `redis.bloom_trusted_ttl_seconds` 的可信时长内，且布隆未命中，就直接按“不存在”返回；如果可信窗口已过，则忽略布隆结果，继续正常查缓存和数据库；详情缓存 key 会先读取该书的 `book:{id}:detail_cache_version`，再拼成 `book:{id}:detail:v{version}`；优先读一级缓存，一级缓存未命中再读 Redis；缓存未命中时会尝试拿 Redis 锁重建缓存；查库后把详情或空值同时回填 Redis 与一级缓存 | 是，缓存未命中时查询 `books` | 会读写一级缓存；会读写 Redis；会使用 Redis 锁；会使用进程内布隆过滤器 |
| GET | `/api/books/search` | 搜索书籍 | 读取 `query / page / pageSize`；空字符串会直接返回空结果；`pageSize` 超过配置上限会直接报错；不走一级缓存，也不走 Redis；如果 `search.rate_limit_enabled=true`，会按客户端 IP 做时间窗口限流；通过校验后直接按标题、作者、ISBN、分类、语言做模糊查询并分页 | 是，每次都会查询 `books` | 不访问一级缓存；开启限流时会访问 Redis 计数器；关闭限流时不访问 Redis |

## 收藏接口

这些接口的业务查询都走数据库；如果接口需要登录，鉴权阶段还会额外访问 Redis `auth_token_version`。

| 方法 | URL | 会做什么 | 主要逻辑 | 是否访问数据库 | 是否访问一级缓存 / Redis |
|---|---|---|---|---|---|
| POST | `/api/users/me/favorites/{book_id}` | 收藏一本书 | 鉴权；先查书是否存在；插入 `user_collected_books`；如果唯一约束冲突，按“已经收藏过”返回成功；随后按数据库真实结果重新查询当前用户完整收藏 id 集合；递增 Redis `user:{id}:favorite_version`，并把带 version 的收藏 id 快照同时写入 Redis `user:{id}:favorite_ids` 与一级缓存 | 是，查询 `books`、`user_collected_books`，写入 `user_collected_books` | 业务本身会递增 Redis 收藏版本并读写 Redis/一级缓存中的收藏快照；鉴权阶段会读写 Redis `auth_token_version` |
| DELETE | `/api/users/me/favorites/{book_id}` | 取消收藏 | 鉴权；按用户 id 和书 id 删除 `user_collected_books` 关系；随后按数据库真实结果重新查询当前用户完整收藏 id 集合；递增 Redis `user:{id}:favorite_version`，并把带 version 的收藏 id 快照同时写入 Redis `user:{id}:favorite_ids` 与一级缓存 | 是，查询并删除 `user_collected_books` | 业务本身会递增 Redis 收藏版本并读写 Redis/一级缓存中的收藏快照；鉴权阶段会读写 Redis `auth_token_version` |
| GET | `/api/users/me/favorites/{book_id}` | 检查当前用户是否已收藏 | 鉴权；先读 Redis `user:{id}:favorite_version`；再比较一级缓存 `user:{id}:favorite_ids` 中的 version；本地 version 匹配就直接判断；否则再读 Redis `user:{id}:favorite_ids`；如果两层快照都不可用，再查数据库并按当前 Redis version 回填收藏 id 快照 | 是，缓存快照不可用时查询 `user_collected_books` | 业务本身会读 Redis 收藏版本；会读写 Redis/一级缓存中的收藏快照；鉴权阶段会读写 Redis `auth_token_version` |
| GET | `/api/users/me/favorites` | 获取当前用户收藏列表 | 鉴权；读取 `page / pageSize`；`pageSize` 超过配置上限会直接报错；联表分页查询当前用户收藏的书籍；随后按数据库真实结果读取当前用户完整收藏 id 集合，并按当前 Redis `user:{id}:favorite_version` 回填 Redis `user:{id}:favorite_ids` 与一级缓存 | 是，查询 `user_collected_books` 和 `books` | 业务本身会读 Redis 收藏版本，并读写 Redis/一级缓存中的收藏快照；鉴权阶段会读写 Redis `auth_token_version` |

## 文件接口

当前文件主流程围绕 `stored_files` 表展开。

`stored_files` 里和接口强相关的状态字段：

- `upload_status`: `init / uploading / uploaded`
- `parse_status`: `not_started / pending / processing / done`
- `bind_status`: `unbound / bound`

正文文件 `kind=book`：

- 同一用户同一时刻只允许有一个未绑定正文文件
- 多次 `POST /api/files/draft` 可能直接复用该未绑定正文文件记录

封面文件 `kind=cover`：

- 允许同时存在多个未绑定封面
- 当前通过 Redis Set 统计“该用户未绑定封面文件 id 集合”的数量，硬编码上限是 5

默认 `mock_upload_enabled=false`，也就是默认走真实对象存储上传流程。

`server-mock` 开启时：

- `upload-session` 返回 mock 会话，前端可跳过真实 `PUT`
- `complete` 不访问 COS，不做真实解析，直接把文件状态改成 `uploaded + done`
- 同时直接写默认解析结果：
  - `title = 原文件名去后缀`
  - `author = 配置项 benchmark.mock_author`
  - `language = 配置项 benchmark.mock_language`
  - `pageCount = 配置项 benchmark.mock_page_count`
  - `coverFileId = null`
  - `rawMetadata.mode = server-mock`
- `download` 统一走固定 mock 对象 key

| 方法 | URL | 会做什么 | 主要逻辑 | 是否访问数据库 | 是否访问一级缓存 / Redis |
|---|---|---|---|---|---|
| POST | `/api/files/draft` | 创建或复用文件记录 | 鉴权；`kind=book` 时，优先查当前用户是否已有未绑定正文文件，有则直接复用；`kind=cover` 时，先看 Redis Set 中未绑定封面数量是否达到上限 5；如果传了 `fileHash`，会按 `user_id + kind + file_hash` 复用未绑定文件；否则新建 `stored_files` 记录；新建封面文件后会把 file id 加入 Redis Set | 是，查询并写入 `stored_files` | 不访问一级缓存；封面场景会读写 Redis Set；鉴权阶段会读写 Redis `auth_token_version` |
| POST | `/api/files/{file_id}/upload-session` | 申请或续签上传链接 | 鉴权；校验文件存在、归属当前用户、且还没绑定到书；用 Redis 锁防并发；如果上传链接还在有效期内且剩余时间大于 5 分钟，就直接返回现有会话；否则按对象 key 生成或续签对象存储预签名上传链接，更新 `stored_files.upload_url / upload_status / upload_expires_at` | 是，查询并更新 `stored_files` | 不访问一级缓存；会使用 Redis 锁；鉴权阶段会读写 Redis `auth_token_version` |
| POST | `/api/files/{file_id}/complete` | 确认上传完成 | 鉴权；校验文件归属和状态；用 Redis 锁防并发；真实模式下调用对象存储 `head_object` 核对文件元数据；如果是正文文件且开启异步解析，会把 `file_parse_results` 置为 `pending` 并投递 RabbitMQ 解析任务；当前发布任务使用进程内复用的 RabbitMQ 连接/Channel，而不是每次新建连接；否则仅把 `parse_status` 置为 `done`；`server-mock` 下不会访问 COS、不会发解析任务，而是直接写默认解析结果并把 `parse_status` 标成 `done`；最后清理文件元数据缓存 | 是，查询并更新 `stored_files`；真实模式下正文文件会写入或更新 `file_parse_results`，`server-mock` 下会写入或更新当前文件的 `file_parse_results` | 会删除 Redis 和一级缓存中的文件元数据缓存；会使用 Redis 锁；鉴权阶段会读写 Redis `auth_token_version` |
| GET | `/api/files/{file_id}/parse` | 查询文件解析结果 | 鉴权；读取 `stored_files` 和对应的 `file_parse_results`，返回上传状态、解析状态、绑定状态，以及解析出的标题、作者、语言、页数、自动封面 `coverFileId`、原始 metadata、错误信息 | 是，查询 `stored_files` 和 `file_parse_results` | 不访问一级缓存；不访问 Redis；鉴权阶段会读写 Redis `auth_token_version` |
| GET | `/api/files/{file_id}/download` | 获取文件访问地址 | 公开文件会先通过混合缓存读取公开文件元数据；缓存命中时不查库；缓存未命中时会尝试拿 Redis 锁重建文件元数据缓存，避免高并发下同一文件元数据一起回源数据库；如果文件尚未发布，但当前登录用户就是文件所有者且文件仍未绑定，也允许直接返回对象存储预签名地址；`server-mock` 下统一返回固定 mock 对象地址 | 是，公开文件缓存未命中时查询 `stored_files`；未发布本人文件场景也会查询 `stored_files` | 公开文件路径会读写一级缓存和 Redis，并会使用 Redis 锁；未发布本人文件路径不依赖文件元数据缓存；如果携带登录态，鉴权阶段会读写 Redis `auth_token_version` |

## 启动阶段相关逻辑

应用启动时会执行一次书籍布隆过滤器预热：

- 从数据库读取所有 `Book.id`
- 放进进程内布隆过滤器
- 预热完成后会刷新一次“布隆可信窗口”截止时间
- 后续每次新建书籍成功时，也会把新 `book_id` 加入当前进程布隆，并刷新这个可信窗口
- 只有在可信窗口内，布隆未命中才会被直接当成“不存在”；超过可信窗口后，详情接口会忽略布隆未命中，继续走缓存和数据库
- 该过程访问数据库
- 不访问一级缓存
- 不访问 Redis

对应代码：

- `fastapi_app/core/app.py`
- `fastapi_app/services/bloom_service.py`

## 异步解析补充

真实模式下，`POST /api/files/{file_id}/complete` 只是把正文文件推进到解析流程里，真正的解析逻辑在 worker 中完成。

worker 做的事：

- 从 RabbitMQ 消费任务
- 用 Redis 锁防止同一个文件重复解析
- 查 `stored_files` 与 `file_parse_results`
- 下载对象存储里的正文文件内容并解析 metadata
- 如果解析出了封面，会新建一条 `stored_files(kind=cover)` 记录，并把封面 id 加入 Redis 未绑定封面集合
- 回写 `file_parse_results`
- 把正文文件的 `parse_status` 改为 `done`

这部分不是直接 HTTP 接口，但会影响下面两个接口的返回结果：

- `POST /api/books`
- `GET /api/files/{file_id}/parse`

`server-mock` 下不会进入这条 worker 解析链路。

## 关于多次登录

当前代码里，多次登录不会让旧 token 失效。

原因是：

- 登录接口不会修改 `users.auth_token_version`
- 登录时只是读取当前 `auth_token_version`，并把它写入 Redis 与一级缓存
- 新旧 token 的 `auth_version` 都一样

真正会让旧 token 失效的动作是：

- `PUT /api/users/me/password`

因为这个接口会把数据库中的 `auth_token_version` 加一，并同步刷新 Redis 与一级缓存。
