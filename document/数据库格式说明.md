# 数据库格式说明

## 说明

当前后端围绕以下 6 张核心表工作：

- `users`
- `stored_files`
- `file_parse_results`
- `books`
- `user_collected_books`
- `uploaded_books`

说明约定：

- `stored_files` 是文件资产主表，同时承担上传状态、解析状态、绑定状态
- `file_parse_results` 正常模式下保存正文文件的解析结果明细；`server-mock` 模式下也可能为 mock 文件写入默认解析结果
- `books` 是最终确认后的业务数据
- 书籍创建后不再支持修改，只支持删除后重建

## 1. users

用途：

- 存储用户账号信息
- 支撑 JWT 鉴权和 token 失效控制

关键字段：

- `id`
- `username`
- `email`
- `password_hash`
- `is_superuser`
- `auth_token_version`
- `created_at`

说明：

- `auth_token_version` 用于让旧 token 在改密码后失效
- JWT 中会写入 `auth_version`
- Redis 中会缓存 `auth_token_version`，但权威值仍然在数据库
- 认证缓存按用户维度组织，推荐理解为：`user:{id}:auth_token_version` 与 `user:{id}:profile`

## 2. stored_files

用途：

- 存储正文文件和封面文件
- 记录上传状态、解析状态、绑定状态
- 作为整个上传流程的主状态表

关键字段：

- `id`
- `user_id`
- `bucket`
- `region`
- `object_key`
- `original_filename`
- `content_type`
- `size`
- `etag`
- `kind`
- `file_hash`
- `ref_count`
- `upload_url`
- `upload_status`
- `parse_status`
- `bind_status`
- `upload_expires_at`

字段说明：

- `kind`：文件类型，当前只允许 `book / cover`
- `upload_status`：上传状态，当前使用 `init / uploading / uploaded`
- `parse_status`：解析状态，当前使用 `not_started / pending / processing / done`
- `bind_status`：绑定状态，当前使用 `unbound / bound`

`upload_status` 状态说明：

| 状态 | 含义 | 主要写入位置 |
|---|---|---|
| `init` | 文件草稿已创建，还没有生成上传会话 | `POST /api/files/draft` 创建 `stored_files` 时写入 |
| `uploading` | 已生成对象存储上传会话，等待前端上传文件 | `POST /api/files/{file_id}/upload-session` 写入 |
| `uploaded` | 文件已上传完成，后端已确认对象存储元数据 | `POST /api/files/{file_id}/complete` 写入；异步解析自动封面入库时也直接写入 |

`parse_status` 状态说明：

| 状态 | 含义 | 主要出现位置 |
|---|---|---|
| `not_started` | 文件草稿刚创建，还没完成上传/解析 | `/api/files/draft` 创建 `stored_files` 时默认值 |
| `pending` | 文件已上传，等待异步解析任务处理 | `/api/files/{file_id}/complete` 中，正文文件且异步解析开启时设置 |
| `processing` | RabbitMQ worker 已取到任务，正在解析 | `parse_worker.process_file_parse()` 开始处理时设置 |
| `done` | 解析流程结束，或该文件不需要解析 | 封面文件上传完成、server-mock、异步解析完成、解析失败记录错误后都会置为 `done` |

`bind_status` 状态说明：

| 状态 | 含义 | 主要出现位置 |
|---|---|---|
| `unbound` | 文件还没被书籍绑定，可以作为草稿文件继续上传/使用 | `/api/files/draft` 创建时默认值；删除书籍时会把文件重新置为 `unbound` |
| `bound` | 文件已经被书籍引用，不能再申请上传会话 | 创建书籍时，正文文件和封面文件都会被置为 `bound` |

说明：

- 正文文件 `kind=book`：
  - 一个用户同一时刻只允许存在一条未绑定正文文件
- 封面文件 `kind=cover`：
  - 允许一个用户同时存在多条未绑定封面文件
  - 当前通过 Redis Set 做软限制，默认上限为 5
- `upload_url` 与 `upload_expires_at` 用于复用未完成上传的同一上传会话
- `parse_status=done` 不等价于解析成功；解析失败时也会进入 `done`，错误原因保存在 `file_parse_results.error_message`
- `bind_status` 与 `ref_count` 配套使用；删除书籍时会先解除绑定并递减引用计数，引用计数归零后删除对象存储文件和 `stored_files` 记录

## 3. file_parse_results

用途：

- 存储正文文件解析结果

关键字段：

- `id`
- `file_id`
- `status`
- `parser_mode`
- `title`
- `author`
- `language`
- `page_count`
- `cover_file_id`
- `raw_metadata`
- `error_message`
- `created_at`
- `updated_at`

说明：

- 一条正文文件最多对应一条解析结果
- `status` 当前使用 `pending / processing / done`，与正文文件的 `stored_files.parse_status` 同步推进
- `cover_file_id` 指向自动提取后生成的封面文件
- 这张表主要服务“解析结果展示 / 草稿编辑”阶段
- 前端可以读取这里的标题、作者、语言、自动封面等结果作为编辑参考
- 当前后端创建 `books` 时不再默认从这张表自动补字段，是否采用这些值由前端决定

## 4. books

用途：

- 保存最终确认后的书籍业务数据

关键字段：

- `id`
- `title`
- `author`
- `isbn`
- `category`
- `year`
- `language`
- `book_file_id`
- `cover_file_id`

说明：

- `book_file_id -> stored_files.id`
- `cover_file_id -> stored_files.id`
- 创建书籍时默认按前端当前提交的字段写入
- 但在 `server-mock` 开启且当前正文文件已有 `file_parse_results` 时，如果前端没有显式传入 `title / author / language`，后端会用解析结果中的这些字段做兜底补齐
- 自动封面 `cover_file_id` 不会从 `file_parse_results` 自动回填到 `books`，是否采用仍由前端决定
- 一旦写入 `books`，后续不再接受自动解析回写

## 5. user_collected_books

用途：

- 用户收藏关系表

关键字段：

- `id`
- `user_id`
- `book_id`

约束：

- 唯一约束：`(user_id, book_id)`

## 6. uploaded_books

用途：

- 用户与其创建书籍之间的关系表

关键字段：

- `id`
- `user_id`
- `book_id`
- `uploaded_at`

约束：

- 唯一约束：`(user_id, book_id)`

## 表关系

核心关系如下：

- `stored_files.user_id -> users.id`
- `file_parse_results.file_id -> stored_files.id`
- `file_parse_results.cover_file_id -> stored_files.id`
- `books.book_file_id -> stored_files.id`
- `books.cover_file_id -> stored_files.id`
- `user_collected_books.user_id -> users.id`
- `user_collected_books.book_id -> books.id`
- `uploaded_books.user_id -> users.id`
- `uploaded_books.book_id -> books.id`

## 当前流程上的表职责

上传流程：

1. 前端先创建或复用 `stored_files`
2. 申请上传链接并写回 `stored_files.upload_url / object_key / upload_expires_at`
3. 上传完成后推进 `stored_files.upload_status / parse_status`
4. 正文文件解析结果写入 `file_parse_results`
5. 用户确认后写入 `books`
6. 书籍和用户关系写入 `uploaded_books`

书籍列表读取流程：

1. 优先支持游标分页，接口可传 `lastId + pageSize`
2. 底层查询使用 `WHERE id < lastId ORDER BY id DESC LIMIT pageSize`
3. 未传 `lastId` 时，为兼容旧调用仍支持 `page + pageSize`
4. 旧分页方式底层仍是 `OFFSET + LIMIT`

## 调试指标

当前支持把调试指标直接写入 Redis，并通过 `/debug/metrics` 聚合查看。

包含的数据主要有：

- 请求级统计
  - 接口调用次数
  - 失败次数
  - 累计耗时与平均耗时
- 缓存命中计数
  - 一级缓存命中
  - Redis 命中
  - 空值命中
  - 未命中
- 下载链路分段耗时
  - 公开文件元数据读取耗时
  - 未发布本人文件查库耗时
  - 预签名下载链接生成耗时
- SQL 指标
  - SQL 执行次数
  - SQL 累计耗时
  - 慢 SQL 次数与慢 SQL 累计耗时
- Redis 锁指标
  - 加锁成功 / 失败 / 异常
  - 释放成功 / miss / 异常

说明：

- 这部分数据不落数据库表
- 只写入 Redis，便于本地压测和问题分析时临时观察

## 总结

当前数据库设计的核心是：

- `stored_files` 管文件和流程状态
- `file_parse_results` 管自动解析结果和草稿参考信息
- `books` 管最终由前端确认后提交的书籍业务数据

这三者的职责已经明确分离：

- 上传阶段看 `stored_files`
- 草稿阶段看 `file_parse_results`
- 正式业务阶段看 `books`

补充：当前缓存层设计

- 认证：用户级 version
  - 数据库字段：`users.auth_token_version`
  - JWT claim：`auth_version`
  - Redis：`user:{id}:auth_token_version`
  - Redis / 一级缓存用户信息：`user:{id}:profile`
  - 一级缓存只保存用户信息，不单独承担认证版本事实源
- 收藏：不使用版本号 key
  - Redis / 一级缓存快照：`user:{id}:favorite_ids`
  - 收藏关系写入或删除提交后，会删除 Redis 和一级缓存中的收藏快照
- 书籍列表 / 搜索 / 总数：不使用版本号 key
  - 书籍创建或删除提交后，会删除 Redis 和一级缓存中的相关列表、搜索和计数缓存
- 书籍列表 / 总数：当前会同时使用一级缓存与 Redis
- 书籍搜索：当前不做缓存，直接查数据库；可通过 `search.rate_limit_*` 配置开启按客户端 IP 的限流保护
- 书籍详情：不使用版本号 key
  - 详情缓存 key：`book:{id}:detail`
  - 书籍删除提交后，会删除 Redis 和一级缓存中的该书详情缓存
  - 详情值当前会同时使用一级缓存与 Redis
